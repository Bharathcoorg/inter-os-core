## 3. Architectural Limitations & Visual Regression Methodology

### 3.1 SMP Evacuation Model Honesty
- **Global Scheduler & Trap Architecture (`AArch64` & `RISC-V 64`):** Both kernels currently maintain a single global `SCHEDULER` mutex, a single global `current_task_idx`, and global trap save areas rather than per-CPU/per-hart runqueues. Concurrent multi-vCPU/multi-hart execution is therefore not supported today.
- **Single-Core QEMU Verification Scope:**
  - All AArch64 QEMU tests (`verify_aarch64_boot.py` and `verify_aarch64_interactive.py`) ran with **one vCPU** (`-M virt`, no `-smp`).
  - All RISC-V 64 QEMU tests (`verify_riscv_boot.py` and `verify_riscv_interactive.py`) ran with **one hart** (`-M virt`, no `-smp`).
  - **No genuine concurrent multi-core evacuation test was executed.** Remote CPU/hart behavior (`reap_task_locksafe` Stage 2 polling, remote `prepare_switch()`, and RISC-V `sbi::remote_sfence_vma`) has **`SOURCE-REVIEWED`** + sequential single-core test coverage only.
- **Passive Bounded Protocol:** `reap_task_locksafe()` uses **bounded polling with the scheduler mutex released between polling attempts** (up to `1000` iterations, `MAX_EVACUATION_POLLS` on AArch64 / `REAP_EVACUATION_MAX_SPINS` on RISC-V 64, keeping `TaskControlBlock::address_space` attached during `TaskState::Reaping`), and `destroy_fallible()` spins up to `100_000` iterations waiting for remote CPUs/harts to transition via `deactivate()`. Active GIC SGI or SBI IPI preemption rendezvous is **`NOT IMPLEMENTED`**; passive bounded evacuation remains a limitation.
- **x86_64 Scope (`kernel/`):** Phase 8.5.4 did not modify `kernel/` (`x86_64`). The `x86_64` kernel remains a single-processor (uniprocessor) system without APIC TLB shootdown IPIs, `reap_task_locksafe()`, `try_activate()` transactional switch rollback, `destroy_fallible()`, `mark_private_frame_unmapped()` ownership validation, or `QUARANTINED_FRAMES` / `is_quarantined()` quarantine protection.

### 3.2 Calculator Structural Pixel-Geometry Assertion
Whole-frame cryptographic hashes (SHA-256) or exact pixel-buffer comparisons are intentionally avoided for display verification because different host GPU drivers, QEMU VNC color depth conversions (RGB565 vs RGB888/BGR), and grayscale anti-aliasing coverage rounding alter raw pixel values without altering user-visible semantics. Instead, `verify_*_interactive.py` evaluates structural glyph geometry over the rendered result display bounding box (checking foreground pixel separation, independent horizontal/vertical stroke components for `'1'` vs `'2'`, aspect ratios, and negative rejection of `"13"`, `"17"`, `"0"`, `"2"`, noise, and bridged digits).
